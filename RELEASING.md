# Releasing

## What a version number means here

Semantic versioning, with the contract stated explicitly, because the usual
reading of it does not fit this tool.

**The contract is the bytes stele writes.** Not its Go API — nothing imports
this as a library, and `internal/` says so. Not its command-line surface alone.
If a repository generates one tree today and a different tree tomorrow from the
same manifest, the same lock and the same plugins, that is a breaking change,
however small the code change was and however clearly the new bytes are better.
The consumer's diff is the same size either way, and their review of it is the
same work.

So, concretely, given `MAJOR.MINOR.PATCH`:

**MAJOR** — a consumer must change something they own, or must review output they
did not ask to change.

- Generated bytes differ for an input that already worked. Including a fix.
  Including a change that makes the output match the reference tool more
  closely. Including whitespace.
- A manifest, lock file or repository layout that used to be accepted is now
  refused, or a command's exit status changes for an input that already worked.
- A command, flag or manifest field is removed or given a different meaning.
- The lock file format changes such that an older stele cannot read a lock a
  newer one wrote, or the reverse.

**MINOR** — a consumer can upgrade, change nothing, and see the same bytes.

- New command, flag or manifest field, with the previous behaviour as the
  default.
- A new input shape is accepted that used to be refused. Nothing that worked
  works differently.
- A defect fixed in a path that could only ever have failed — a run that errored
  now succeeds. Nobody was depending on the error's absence of bytes.

**PATCH** — nothing a consumer can observe except that something wrong is now
right, in a way that cannot change a successful run.

- Error messages, help text, the version report, documentation.
- Performance.
- A fix to a code path no supported input reaches.

**When in doubt, go up.** The cost of an unnecessary major is that someone reads
a changelog entry that says "nothing changed for you". The cost of a missed one
is a fleet-wide diff nobody was told about.

### While the major version is 0

`0.MINOR.PATCH` compresses the scale by one: what would be MAJOR above bumps
MINOR, and everything else bumps PATCH. That is the ordinary Go convention and
it is honest about the state of the evidence — see below. It does not soften the
rule: a `0.x` release that changes generated bytes still says so in the
changelog under `Generated output`, and still bumps the field that signals
"read this before upgrading".

## Why the first release is v0.1.0 and not v1.0.0

The argument for `v1.0.0` is real and worth stating: the tool is not a
prototype. `generate` matches the reference tool byte for byte on twelve
repositories including managed mode, two repositories run on it in real CI, one
of them a fleet's acceptance suite, and dependencies and plugins are pinned and
verified. That is more evidence than a good many `1.0` releases carry.

It is still not enough, for two reasons that are about evidence rather than
polish:

1. **`export` parity is proven on one repository.** It is the half that removes
   the registry, and it is the half least tested — one repository, 48 files. A
   `1.0` promises that the next `1.x` will not change those bytes, and we cannot
   yet see enough shapes of `export` to know which of its current behaviours are
   decisions and which are accidents. Promising compatibility for behaviour you
   have not characterised is how a major version becomes a lie.
2. **Parity is not yet held by the tool's own CI.** It is proven by hand, on one
   machine, against a corpus in a temporary directory (roadmap milestone 3). A
   regression in the contract would reach a user before it reached us. A
   stability promise that nothing enforces is a promise about intentions.

`v1.0.0` is the release that follows roadmap milestones 3 and 4: parity running
on every change, and `export` parity beyond one repository. Until then `0.x`
states the truth — the bytes may still move, and when they do you will be told.

## Cutting a release

1. Update `CHANGELOG.md`: move `Unreleased` into a section for the new version,
   with the date. Check `Generated output` honestly — if it is empty, that is a
   claim, and it should be one somebody verified against the parity corpus, not
   one that was empty because nobody looked.
2. Choose the number by the rules above.
3. Commit, and tag: `git tag -a vX.Y.Z -m "vX.Y.Z"`.
4. Push the tag. The `Release` workflow does the rest.

The workflow can also be run by hand (`workflow_dispatch`) against an existing
tag, which is how it was exercised before the first real release.

## What the workflow guarantees

- **A tag cannot publish a broken build.** `gofmt`, `go vet` and `go test ./...`
  run before anything is built, in the same job.
- **A published binary cannot claim a version it was not built from.** There is
  no `-ldflags` stamping. The Go toolchain records the tag by itself, and the
  workflow then runs the freshly built binary and refuses to publish unless it
  reports exactly the tag being released. A checkout that lost the tag, or a
  build that lost its VCS information, fails the release rather than shipping a
  binary that says `(devel)`.

### Version stamping, and why there is no `-ldflags`

Since Go 1.24 the toolchain stamps the module version into the binary from the
repository itself, and `debug.ReadBuildInfo` reads it back. Measured on go1.26
in this repository:

| build | reported version |
| --- | --- |
| at a tag, clean tree | `v0.1.0` |
| away from a tag, clean tree | `v0.0.0-20260823183642-7c47cad85fcf` |
| modified tree | `v0.1.0+dirty` |
| `-buildvcs=false` | `(devel)` |
| `go install …@v0.1.0` | `v0.1.0` |

Every case a release needs is already distinguishable, and `report.IsRelease`
is the predicate over them. An `-X` flag would be a second, independent copy of
a fact the toolchain already has: right only when whoever ran the build
remembered to pass it, silently wrong when they did not. Forgetting it ships a
release that calls itself a development build; passing it by hand on a dirty
tree ships a development build that calls itself a release. Removing the flag
removes both, and the verify step covers what remains.

## Reproducibility

Two builds of one tag produce identical binaries. What makes that true:

- `-trimpath`, so the build machine's directory layout is not in the binary.
- `CGO_ENABLED=0`, so the host C toolchain is not an input.
- The Go version pinned exactly (`1.26.0`, `check-latest: false`), because the
  compiler is an input to the bytes and `1.26` would silently become a different
  compiler between two builds of the same tag.
- `-buildvcs=true`, left on deliberately: it is what stamps the version, and for
  a given tag it stamps the same revision and the same commit timestamp every
  time, so it does not cost reproducibility.
- Dependencies pinned by `go.sum`.

The workflow does not merely claim this. It builds `linux/amd64` twice and fails
the release if the two SHA-256 digests differ.

**What is not covered.** Reproducibility is guaranteed for the same Go version
on the same builder OS. A different Go patch release will produce different
bytes, by design — that is why it is pinned rather than floating, and why the Go
version used for a release is worth recording when a binary is ever
re-derived. Cross-compilation from a different host OS is untested; the
published binaries are all built on `ubuntu-latest`, and the check above is what
holds that constant.

## Platforms, and why these four

| platform | who consumes it |
| --- | --- |
| `linux/amd64` | the CI images this tool was built to run in; the majority case by a wide margin |
| `linux/arm64` | arm CI runners, and Linux workstations on arm |
| `darwin/arm64` | developer machines — Apple Silicon |
| `darwin/amd64` | developer machines — the Intel Macs still in service |

The rule is that a platform is published when somebody runs the tool on it. Two
groups do: CI, which is Linux, and developers, who are on Linux and macOS. Both
architectures are published for each because the arm/x86 split is live in both
groups and guessing wrong costs an adopter a Go toolchain, which is the thing
these binaries exist to avoid.

**Windows is absent**, and not because it would be hard: Go cross-compiles it
for free. It is absent because nothing that consumes this tool runs on it and
nothing here has ever been tested there. The tool shells out to `git` and its
manifests carry slash-separated paths; whether those hold on Windows is
unknown, and publishing a binary is a claim that somebody checked. Adding it is
a small change to this workflow the day a consumer appears — and it should come
with a CI job on `windows-latest`, not on its own.
