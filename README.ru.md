# stele

**Контракты protobuf, которые доставляются через git.** Генерация кода, экспорт
схем, линтер контрактов и поиск ломающих изменений — зависимости берутся прямо
из git-репозиториев, без реестра схем посередине.

[![CI](https://github.com/thegorangers/stele/actions/workflows/ci.yml/badge.svg)](https://github.com/thegorangers/stele/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/thegorangers/stele)](https://github.com/thegorangers/stele/releases)
[![Licence](https://img.shields.io/badge/licence-Apache--2.0-blue)](LICENSE)

[English](README.md) · **Русский**

```yaml
# stele.yaml
version: 1
modules:
  - path: proto
deps:
  - name: orders
    git: https://gitlab.example.ru/acme/orders.git
    ref: v2.0.1
generate:
  - name: go
    inputs:
      - module: proto
    plugins:
      - local: protoc-gen-go
        module: google.golang.org/protobuf/cmd/protoc-gen-go
        version: v1.36.12
        out: gen
        opt: paths=source_relative
```

```console
$ stele generate
```

## Зачем

**Зависимость — это git-репозиторий, ref и корень модуля.** Никакого реестра
посередине нет, и он не планируется: не нужно заводить аккаунт, поднимать
сервис или пускать третью сторону между вами и схемой, доступ к которой у вас
и так есть. Аутентификацией занимается системный `git` — работают ssh-агенты,
credential helpers и `insteadOf`, потому что stele вызывает тот инструмент,
который уже знает ваши доступы.

**Инструмент отказывается, а не догадывается.** Неизвестный ключ конфигурации
или флаг — ошибка с именем этого ключа. Миграция, которая не смогла что-то
перевести, завершается ненулевым кодом и перечисляет нерешённое. Запуск, не
создавший ни одного файла, считается провалом, а не успехом. Конфигурация,
понятая наполовину, даёт результат, неправильный наполовину, — лучше
остановиться.

**Всё, что влияет на итоговые байты, зафиксировано.** Зависимости
разрешаются в конкретные коммиты и записываются в `stele.lock`; плагины
пиннятся модулем и версией либо digest'ом для каждой платформы, ставятся в
собственный кэш stele и проверяются после установки. `stele version` печатает
все входные данные, определившие результат запуска.

## Импортозамещение buf

Практическая причина, по которой этот инструмент может быть интересен командам
в России: **у buf схемы живут в Buf Schema Registry — это SaaS американской
компании**. Зависимость от внешнего сервиса, которым вы не управляете, — это и
риск доступности, и вопрос к контуру, в котором лежат ваши контракты.

Что здесь по-другому:

- **Реестра нет вообще.** Схема берётся из git — вашего GitLab, Gitea,
  Gerrit или чего угодно, что умеет отдавать репозиторий по `https://` или
  `ssh://`. Никаких обращений к внешним сервисам за схемами.
- **Работает в закрытом контуре.** Единственная сеть, которая нужна, — до
  ваших же git-серверов и до источника плагинов; плагины можно закэшировать
  заранее (`stele plugins install`) и дальше собирать без сети вовсе.
- **Ничего не привязано к вендору.** Формат манифеста — `version: 1`,
  открытая схема JSON Schema в репозитории; лицензия Apache-2.0; сборка
  воспроизводима из исходников.
- **Переход не с нуля.** `stele migrate` переводит существующую пару
  `buf.yaml` / `buf.gen.yaml` в `stele.yaml` и честно отказывается, если
  что-то перевести не смог.

Честные оговорки, без которых это была бы реклама, а не описание:

- Совместимость с buf **не полная и не обещается** — поддерживается
  измеренное подмножество формата конфигурации, всё остальное отвергается по
  имени. Что именно поддержано — в [руководстве](docs/GUIDE.md#honest-boundaries).
- Инструмент **использует иностранные open-source библиотеки**:
  `google.golang.org/protobuf` (Google) и `github.com/bufbuild/protocompile` —
  последнюю написала как раз Buf. Это библиотеки под свободными лицензиями,
  вендорящиеся в сборку, а не сервисы, к которым нужно ходить по сети; но
  называть проект полностью независимым от иностранного кода было бы
  неправдой.
- Сам репозиторий сейчас размещён на **GitHub**, релизы публикуются там же.
- В реестр российского ПО инструмент **не внесён**.

Цель, ради которой всё затевалось, — побайтовое совпадение с buf на том, что
обе программы умеют, чтобы переход не менял ни одного сгенерированного файла.
Проверяется приёмочным набором на закреплённой версии buf; запускается
командой `go test -tags parity ./test/parity/`.

## Установка

Бинарники для `linux/amd64`, `linux/arm64`, `darwin/amd64` и `darwin/arm64` —
на [странице релизов](https://github.com/thegorangers/stele/releases).
Go-тулчейн для запуска не нужен.

```bash
tag=v0.5.0 os=linux arch=amd64
base="https://github.com/thegorangers/stele/releases/download/$tag"
curl -fsSLO "$base/stele_${tag}_${os}_${arch}"
install -m 0755 "stele_${tag}_${os}_${arch}" /usr/local/bin/stele
```

С Go-тулчейном:

```bash
go install github.com/thegorangers/stele/cmd/stele@v0.5.0
```

<details>
<summary><b>Проверка подписи релиза</b> (рекомендуется)</summary>

Файл `SHA256SUMS` подписан [cosign](https://github.com/sigstore/cosign) в
keyless-режиме — открытый ключ скачивать не нужно. Сам по себе хэш
подтверждает только то, что файл скачался целым: тот, кто может опубликовать
релиз, может опубликовать и подходящий `SHA256SUMS` рядом. Подпись
подтверждает полезное: эти байты вышли из релизного workflow именно этого
репозитория, на этом теге.

```bash
curl -fsSLO "$base/SHA256SUMS" "$base/SHA256SUMS.sig" "$base/SHA256SUMS.pem"

cosign verify-blob SHA256SUMS \
  --signature SHA256SUMS.sig \
  --certificate SHA256SUMS.pem \
  --certificate-identity-regexp \
    '^https://github.com/thegorangers/stele/\.github/workflows/release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# Только теперь хэш что-то значит.
sha256sum --ignore-missing -c SHA256SUMS
```

Порядок важен: `sha256sum -c` против непроверенного `SHA256SUMS` сверяет
скачанное с утверждением из того же источника. Бинарники воспроизводимы из
исходников — см. [RELEASING.md](RELEASING.md).
</details>

**Требования:** бинарь `git` в `PATH` во время работы; Go 1.26+ — только для
сборки из исходников.

## Быстрый старт

**1. Создайте `stele.yaml`** в корне репозитория. Минимальный рабочий манифест —
три строки:

```yaml
version: 1
modules:
  - path: proto
```

Блок `generate:` добавляет генерацию кода, блок `deps:` — схемы из других
репозиториев, как в примере в начале страницы.

**2. Сгенерируйте.** Плагины ставятся сами при первом запуске:

```bash
stele generate
```

`protoc-gen-go` требует, чтобы в каждом файле был `option go_package` — так же,
как и под любым другим инструментом; префикс можно задать блоком `managed:`,
тогда в `.proto` его писать не нужно. Команда кладёт сгенерированный код в
каталог `out` каждого плагина и записывает в `stele.lock` коммит, в который
разрешилась каждая зависимость. Этот файл коммитьте: последующие запуски берут
зафиксированные коммиты, а перезапрашивает их флаг `--update`.

**3. Подключите проверки в CI.**

```bash
stele lint                    # правила контрактов для того, чем владеет репозиторий
stele breaking --base main    # сравнение с правильной предыдущей ревизией
```

`stele breaking` сравнивает с merge-base относительно базовой ветки, если вы на
тематической ветке, или с первым родителем, если уже на базовой, — ревизию
руками указывать не нужно. Нужна полная история: если CI клонирует поверхностно,
сначала выполните `git fetch --unshallow`.

Внедряете линтер на репозитории, который ещё не чист? `stele lint
--update-baseline` запишет `stele.baseline` — он принимает сегодняшние находки,
и падать сборка будет только на новых. Файл коммитится и ревьюится как любой
другой.

## Переход с buf

```bash
stele migrate            # печатает переведённый манифест
stele migrate --write    # записывает stele.yaml
```

Читаются `buf.gen.yaml`, `buf.yaml`, а также `Makefile` — обычно это
единственное место, где записано, откуда взялись плагины, — и ваши собственные
`.proto`, чтобы понять, какие сторонние модули вы действительно импортируете.

**Миграция, оставившая что-то нерешённым, завершается ошибкой** и перечисляет
всё поимённо: импорт без объявленного источника, незафиксированный экспорт,
плагин, версию которого не удалось свести к точной. Ничего не выдумывается,
чтобы закрыть дыру: манифест, который выглядит перенесённым, но таковым не
является, хуже, чем его отсутствие.

Блоки `lint` и `breaking` из конфигурации buf читаются, но не переносятся —
наборы правил разные, и перевод был бы догадкой. Их нужно настроить заново в
`stele.yaml`.

## Команды

| Команда           | Что делает                                                                     |
| ----------------- | ------------------------------------------------------------------------------ |
| `stele generate`  | Компилирует `.proto` и запускает ваши плагины генерации кода                    |
| `stele export`    | Выкладывает `.proto` файлы зависимости в каталог                                |
| `stele lint`      | Проверяет контракты этого репозитория по правилам                               |
| `stele breaking`  | Сравнивает с предыдущей ревизией и сообщает о ломающих изменениях               |
| `stele migrate`   | Переводит пару `buf.yaml` / `buf.gen.yaml` в `stele.yaml`                       |
| `stele plugins`   | Ставит объявленные в манифесте плагины или показывает, какой бинарь будет вызван |
| `stele version`   | Печатает версии, определяющие сгенерированные байты                             |

У всех команд есть `--help`; у тех, что читают манифест, — ещё `--dir DIR` и
`--cache-dir DIR` (по умолчанию `$XDG_CACHE_HOME/stele`, иначе `~/.cache/stele`;
переменная `$STELE_CACHE_DIR` учитывается). Полный справочник по флагам — в
[руководстве](docs/GUIDE.md).

## Поддержка редакторов

JSON Schema для `stele.yaml`, `stele.lock` и `stele.baseline` лежат в
[`schema/`](schema/). Одна строка в начале манифеста включает автодополнение и
валидацию:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/thegorangers/stele/main/schema/stele.schema.json
```

## Известные ограничения

Стоит знать до того, как полагаться на инструмент:

- **У `stele breaking` есть слепая зона**, и она печатается в каждом отчёте:
  переименование `json_name`, расширение `int32` до `int64` под protojson и
  изменения `google.api.http` проходят зелёными. Если у вас gRPC-транскодинг,
  прочитайте [про слепую зону](docs/GUIDE.md#the-blind-zone).
- **Линтер — первый срез**: пять правил `aip/` по трём AIP плюс общие правила
  контрактов. Что вообще решается по дескриптору, а что нет, перечислено в
  [docs/AIP.md](docs/AIP.md).
- **`stele lint` судит только то, чем владеет репозиторий.** Зависимости
  компилируются, но не проверяются.
- **Windows не поддерживается**, сознательно.
